提案手法の読み方

仕組みより先に、前提を読む

  • 手法を入力・処理・出力に分解して理解できる
  • 著者が置いている前提・仮定を漏れなく拾える
  • 記述から再現可能性を判断できる

操作：← → / Space でページ送り　O キーでスライド一覧

読む順序Reading order

細部から読まない。外側から内側へ。

  1. 前提・仮定を先に読む
    何を所与とし、何を対象外としているか。これが分からないと、以降すべてが宙に浮く
  2. 入力と出力を確定させる
    何を受け取り、何を返すのか。1 行で書けるまで読む
  3. 全体構成の図を読む
    構成要素の数と、要素間のデータの流れ
  4. 各要素の中身を読む
    自分に必要な要素だけでよい
  5. 動作例があれば必ず読む
    具体値で一連の処理を追える。理解の確認になる
理解できたかのテスト その手法の図を、論文を見ずに自分で描けるか。 描けなければ、まだ理解していない。描けたら、論文の図と見比べる。

前提と仮定を拾うAssumptions

手法の価値は、どんな前提のもとで成り立つかで決まる。

拾うべき前提
  • 入力の前提：対象は取得可能か、形式は何か
  • 環境の前提：必要な計算資源、ネットワーク条件
  • データの前提：ラベル付きデータが入手できるか
  • 攻撃者の前提：何を知っていて、何ができるか（トピック 13）
  • 信頼の前提：誰を／何を信頼するか
  • 対象外：扱わないと明言されているもの
前提を示す定型表現

〜を前提とする／〜と仮定する
〜は本研究の範囲外である
〜については扱わない
〜が利用可能であるものとする
本手法は〜の場合に適用できる

We assume that ...
... is out of scope of this work
We consider an adversary who ...
Without loss of generality, we ...

前提が書かれていない場合 「前提がない」のではなく「書かれていない」と読む。 どんな手法にも必ず前提はある。書かれていなければ、 その手法の適用範囲は判断できないと記録する。

記号と定義に躓かないNotation

数式が読めないのではなく、記号の意味を見失っているだけのことが多い。

　入力ページの DOM を T とし、T に含まれる要素ノードの集合を V(T) と表す。また、外部リソースを参照する要素の集合を E(T) ⊆ V(T) とする。

　外部リソースのドメイン分散度 d(T) を、次式で定義する。

d(T) = |{ dom(e) | e ∈ E(T) }| / |E(T)| 　　(1)

　ここで dom(e) は要素 e が参照する URL のホスト名を表す。

  1. 記号の対応表を自分で作る
    T＝DOM、E(T)＝外部参照要素の集合、d(T)＝ドメイン分散度
  2. 式を日本語に訳す
    式(1)＝「参照先ドメインの種類数を参照総数で割った値」
  3. 値の範囲と意味を考える
    0 < d ≤ 1。1 に近い＝参照先がばらばら
  4. 具体値を入れてみる
    17 要素が 9 ドメインを参照 → d = 9/17 ≈ 0.53
定義されていない記号 前の章や参考文献で定義されていることがある。 探しても見つからなければ、「定義されていない」と記録する。推測で補わない。

再現できるかを判断するReproducibility

「この記述だけで、自分は同じものを実装できるか」を問いながら読む。

確認する項目書かれていなければ
入力の形式何を渡せばよいか分からない
処理の手順擬似コードやアルゴリズムがあるか。なければ順序が曖昧
ハイパーパラメータ同じ結果は出ない。学習率・エポック数・乱数シード
使用ライブラリとバージョン挙動が変わる可能性がある
前処理データの整形方法で結果は大きく変わる
閾値の決め方「適切に設定した」だけでは再現できない
コード・データの公開URL があるか。あれば最優先で見る
公開コードは最良の「続き」 論文に書かれていない実装の詳細は、公開リポジトリにある。 セキュリティ分野の主要会議には Artifact Evaluation があり、 再現性が確認された論文にはバッジが付いていることがある。

「なぜそれで解決するのか」を探すThe mechanism

手順が分かっただけでは、理解したことにならない。効く理由が書かれているかを見る。

手順だけ

提案手法では、HTML から 27 次元の構造特徴量を抽出し、勾配ブースティング決定木により分類する。

なぜ短縮 URL に効くのかが書かれていない。 読者は「効く理由は本文から読み取れない」と記録する。

機序が書かれている

HTML 構造特徴量は、攻撃者が使い回すテンプレートに由来するため、URL を変更しても変化しにくい。この性質により、URL 短縮によって語彙的特徴量が失われる場合でも、判別に必要な情報が保たれる。

前提（テンプレートの使い回し）と機序（URL 変更で変化しない）が明示されている。 → この前提が崩れたら手法も崩れる、と分かる。

読者が得るもの 機序が分かると、「どんな場合にこの手法が破れるか」が自分で考えられるようになる。 上の例なら「攻撃者がテンプレートを毎回変えたら？」という問いが立つ。 それが、あなたの次の研究テーマになる。
